# 20.3 — Question Extraction

Esta etapa define como identificar, extrair e estruturar perguntas presentes em uma transcrição de entrevista, utilizando os participantes e a autoria já determinados por [[20.1 - Participant Identification]] e [[20.2 - Speaker Attribution]].

Ela é uma especialização do [[Transcription Processing Model]] e deve permanecer separada de [[Question Taxonomy]], [[Evidence Model]] e [[Evaluation Engine]].

## 1. Objetivo e fluxo

A pergunta central desta etapa é:

```text
O que foi perguntado?
```

Fluxo:

```text
20.1 — Participant Identification
        ↓
20.2 — Speaker Attribution
        ↓
20.3 — Question Extraction
        ↓
Perguntas estruturadas
        ↓
20.4 — Response Extraction
        ↓
20.5 — Reconstruction & Normalization
        ↓
20.6 — Question/Response Linking
        ↓
20.7 — Validation
```

O módulo deve produzir unidades de pergunta rastreáveis, preservando o texto original, o speaker, a posição temporal, follow-ups, reformulações, perguntas compostas, interrupções, ausência de resposta e incertezas.

## 2. Separação de responsabilidades

```text
Participant Identification
→ Quem são as pessoas?

Speaker Attribution
→ Quem falou cada trecho?

Question Extraction
→ Qual trecho constitui uma pergunta?

Response Extraction
→ Qual trecho constitui uma resposta?

Question/Response Linking
→ Qual resposta corresponde a qual pergunta?

Evidence Extraction
→ Que evidências existem na resposta?

Evaluation Engine
→ Como essas evidências devem ser avaliadas?
```

O `Question Extraction` não deve:

- avaliar o candidato, a pergunta ou a resposta;
- atribuir notas ou inferir senioridade;
- interpretar competência técnica;
- decidir se o candidato conhece determinado assunto;
- corrigir tecnicamente a pergunta;
- inventar informações ausentes;
- criar uma pergunta que não seja sustentada pela transcrição;
- concluir que uma pergunta é boa, ruim, fácil ou difícil.

## 3. Regra fundamental: extrair não é reconstruir

> **Extrair a pergunta é diferente de reconstruir ou interpretar a pergunta.**

O agente pode normalizar pontuação, remover ruído evidente e corrigir erro linguístico inequívoco. Também pode reconhecer um termo técnico claramente corrompido quando o contexto elimina interpretações plausíveis alternativas.

Não pode adicionar requisitos, completar uma frase porque conhece a resposta esperada, tornar uma pergunta mais complexa ou utilizar a base técnica para fabricar conteúdo.

```text
Corrigir forma é permitido.
Criar conteúdo não é permitido.
```

Exemplo permitido:

```text
Como você utilizaria o Azure Montor?
→
Como você utilizaria o Azure Monitor?
```

Somente quando o contexto tornar a interpretação inequívoca. O `original_text` deve ser preservado quando houver normalização relevante.

Exemplo proibido:

```text
Qual a diferença entre...
→
Qual a diferença entre Azure Monitor e Application Insights?
```

O segundo texto adiciona conteúdo que não está presente.

## 4. O que constitui uma pergunta

Reconhecer uma pergunta pela intenção conversacional sustentada pelo trecho e pelo contexto, não apenas pela presença de `?`.

### 4.1 Pergunta explícita

```text
Você já trabalhou com Java 17?
```

### 4.2 Pergunta sem ponto de interrogação

```text
Me explica como você utilizaria o Azure Monitor.
```

O formato imperativo funciona como solicitação de resposta e deve ser extraído como pergunta.

### 4.3 Pergunta indireta

```text
Queria entender como você investigaria esse tipo de erro.
```

Se o contexto mostrar que o interlocutor está solicitando uma explicação, extrair como pergunta. Se for apenas uma afirmação sobre interesse, preservar como fala não interrogativa.

### 4.4 Pergunta conversacional

```text
E nesse caso, o que você faria?
```

Pode ser uma pergunta independente ou um follow-up; a relação depende do contexto imediatamente anterior.

### 4.5 Pergunta de experiência

```text
Você já trabalhou com Application Insights?
```

Extrair a pergunta sem concluir se existe ou não experiência.

### 4.6 Pergunta técnica e pergunta de cenário

```text
Qual a diferença entre @Produces e @Consumes?

Imagine que a aplicação começou a apresentar aumento de latência.
Como você investigaria?
```

O módulo identifica a unidade interrogativa. A classificação técnica, o domínio e a complexidade pertencem à [[Question Taxonomy]].

## 5. Perguntas implícitas e afirmações

Uma fala declarativa pode conter uma intenção de pergunta quando o contexto fornece evidência suficiente:

```text
Você recebe vários erros 500 em produção...
E aí, o que faria?
```

Extrair a pergunta efetivamente presente. Não transformar toda afirmação em pergunta:

```text
Na nossa aplicação usamos Azure Monitor.
```

Essa fala é uma afirmação, salvo se outra parte do trecho indicar uma solicitação explícita de resposta.

Não usar o simples fato de a fala ocorrer em uma entrevista como motivo suficiente para classificá-la como pergunta.

## 6. Perguntas compostas

Uma pergunta pode conter vários componentes:

```text
Você já trabalhou com Azure Monitor?
Como utilizava?
E quais problemas costumava investigar com ele?
```

### 6.1 Manter como uma pergunta composta quando

- os componentes formam uma única solicitação contínua;
- a segunda parte apenas detalha a primeira;
- a interrupção entre frases não muda a unidade conversacional;
- separar criaria perguntas artificiais sem benefício de rastreabilidade.

### 6.2 Separar em perguntas relacionadas quando

- há mudança clara de solicitação;
- cada parte pode receber resposta independente;
- há mudança de assunto ou de foco;
- o entrevistador inicia uma nova pergunta após a resposta ou confirmação;
- a estrutura posterior precisa associar respostas diferentes.

Quando houver dúvida, preservar a sequência e marcar `needs_review: true`, em vez de dividir arbitrariamente.

## 7. Subperguntas e follow-ups

Reutilizar a convenção já definida no Stage 20:

```text
Q5
Você já trabalhou com Azure Monitor?

Q5.1
Como você utilizava?

Q5.2
Quais problemas costumava investigar?
```

Usar `follow_up_of` para registrar a dependência:

```yaml
question_id: Q5.1
follow_up_of: Q5
```

Um follow-up aprofunda ou restringe a pergunta anterior; não é automaticamente uma nova unidade independente. Contudo, uma pergunta inicialmente relacionada pode se tornar independente se houver mudança clara de tema ou se o contexto reiniciar a investigação.

Exemplo:

```text
Q4: Você já trabalhou com Java?
Q4.1: Qual versão?
Q4.2: E você utilizava quais recursos?
Q4.3: Pode dar um exemplo?
```

## 8. Reformulação de pergunta

Não apagar a pergunta original quando o entrevistador a reformular:

```text
Q6:
Você já trabalhou com Kubernetes?

Q6.1:
Quer dizer, já trabalhou com algum orquestrador de containers?
```

Quando a segunda formulação substitui ou esclarece a primeira, registrar:

```yaml
question_id: Q6.1
reformulation_of: Q6
```

Se a reformulação apenas acrescentar um follow-up, usar `follow_up_of` em vez de `reformulation_of`. A decisão deve representar a relação conversacional, não apagar a sequência temporal.

## 9. Perguntas interrompidas e parcialmente transcritas

Considere:

```text
Entrevistador:
Você já trabalhou com...

Candidato:
Sim.

Entrevistador:
...Application Insights?
```

Se os segmentos forem atribuídos ao mesmo speaker e a continuidade for inequívoca, podem compor uma única pergunta estruturada, preservando os segmentos de origem:

```yaml
question_id: Q7
question: "Você já trabalhou com ... Application Insights?"
original_text: "Você já trabalhou com... ...Application Insights?"
question_status: partially_identified
extraction_confidence: medium
needs_review: true
```

Não preencher o trecho omitido com conteúdo não transcrito. Se a pergunta só puder ser compreendida após uma reconstrução posterior, o módulo deve preservar a unidade parcial e deixar a reconstrução para a etapa apropriada.

Para uma fala sem continuação:

```text
Como você faria para investigar...
```

registrar somente o conteúdo disponível:

```yaml
question_status: partially_identified
needs_review: true
```

Não completar com a tecnologia mais provável ou com uma pergunta esperada pelo avaliador.

## 10. Erros de transcrição e termos técnicos

O Second Brain pode apoiar o reconhecimento de termos técnicos, mas não pode ser usado para completar perguntas.

Normalização aceitável:

```text
Você já trabalhou com Azure Montor?
→
Você já trabalhou com Azure Monitor?
```

Essa normalização exige contexto suficientemente forte. Preservar `original_text` e registrar `needs_review` quando a grafia ainda admitir mais de uma interpretação.

Exemplo ambíguo:

```text
Você já trabalhou com monitor?
```

Pode significar Azure Monitor, monitoramento ou outro conceito. Não escolher arbitrariamente.

## 11. Perguntas de experiência e não técnicas

Extrair perguntas de experiência sem transformar a extração em avaliação:

```text
Você já trabalhou com Java?
Você tem experiência com Azure?
Já precisou investigar problemas de produção?
Como era sua atuação nesses incidentes?
```

Também preservar perguntas comportamentais, administrativas e não técnicas:

```text
Como você lida com um incidente crítico?
Como costuma trabalhar com outras equipes?
O que você faz quando não conhece um problema?
```

O módulo não conclui `candidate has experience`, `candidate lacks experience` ou qualquer equivalente. Essas interpretações pertencem ao [[Evidence Model]] e ao [[Evaluation Engine]].

## 12. Perguntas feitas pelo candidato e por participantes adicionais

Qualquer participante pode formular uma pergunta:

```text
Candidato:
Como funciona o processo de deploy aqui?
```

Extrair a pergunta e preservar:

```yaml
speaker:
  participant_id: candidate
```

O fato de o speaker ser `candidate` não transforma a pergunta em pergunta técnica usada para avaliação. Ela deve apenas ser preservada para classificação posterior.

O mesmo se aplica a entrevistador técnico, entrevistador adicional, coordenador, RH, observador ou participante desconhecido. Registrar quem perguntou sem assumir que toda pergunta é avaliativa.

## 13. Afirmação seguida de pergunta

Separar contexto declarativo e pergunta:

```text
Entrevistador:
Aqui usamos bastante Azure Monitor.
Você já trabalhou com ele?
```

Resultado:

```text
Contexto: Aqui usamos bastante Azure Monitor.
Q8: Você já trabalhou com ele?
```

O contexto não deve ser incorporado ao texto da pergunta, salvo se os próprios segmentos formarem uma única frase interrogativa. Se o modelo posterior precisar do contexto, ele deve referenciar o segmento original; não criar uma cópia artificial dentro de `question`.

## 14. Pergunta seguida de comentário ou intervenção

Separar a pergunta de comentários do entrevistador:

```text
Você já trabalhou com Java 21?
É algo que usamos bastante aqui.
```

A primeira fala é a pergunta. A segunda é comentário contextual.

Para múltiplas intervenções:

```text
Q1: Como você investigaria um erro 500?
Rascunho de resposta: Eu começaria olhando os logs.
Comentário: Certo.
Q1.1: E se não encontrasse nada?
```

O Question Extraction identifica `Q1` e `Q1.1`, mas não extrai nem avalia a resposta. A classificação de `Rascunho de resposta` e o vínculo final pertencem aos módulos seguintes.

## 15. Perguntas retóricas e de condução

Preservar perguntas estruturalmente presentes, mesmo quando não forem perguntas técnicas avaliativas:

```text
A gente não deveria olhar os logs primeiro?
Entendeu?
Tudo bem?
Você sabe que o Azure Monitor tem métricas, certo?
```

O módulo deve registrar o texto e o speaker, mas não decidir se a fala é:

- pergunta avaliativa;
- confirmação;
- pergunta retórica;
- pergunta de condução;
- pergunta técnica;
- pergunta comportamental;
- pergunta casual.

Essa classificação pertence à etapa de taxonomia ou ao processamento semântico apropriado. Uma pergunta retórica não implica que exista uma resposta esperada ou que o candidato devesse respondê-la.

## 16. Estados da pergunta e confiança da extração

Reutilizar os estados previstos no Stage 20 e detalhá-los para esta etapa:

```text
identified
partially_identified
uncertain
missing
```

- `identified`: o trecho constitui uma pergunta e seu conteúdo está suficientemente claro;
- `partially_identified`: há uma pergunta, mas parte do conteúdo está ausente ou interrompida;
- `uncertain`: não é possível determinar com segurança se o trecho constitui uma pergunta ou qual é sua unidade;
- `missing`: existe uma referência estrutural a uma pergunta, mas o trecho necessário não está disponível.

Usar:

```yaml
extraction_confidence: high | medium | low
```

- **high**: intenção interrogativa e limites da pergunta são claros, com speaker e origem identificáveis;
- **medium**: a pergunta é plausível e estruturável, mas há ambiguidade pontual, reformulação ou ruído;
- **low**: a intenção, os limites ou o conteúdo são incertos; marcar revisão.

Essa confiança representa somente a segurança da extração, não a qualidade da pergunta, sua dificuldade ou a qualidade da resposta.

```text
participant_identification_confidence
≠
speaker_attribution_confidence
≠
question_extraction_confidence
≠
reconstruction_confidence
≠
evaluation_confidence
```

## 17. Question ID e sequência

Usar identificadores estáveis conforme o Stage 20:

```text
Q1
Q2
Q3
Q3.1
Q3.2
```

Os IDs existem exclusivamente para rastreabilidade, vínculo com respostas, referência entre módulos e geração de relatório. Não representam qualidade, dificuldade, importância, mérito, nota ou senioridade.

Preservar a ordem temporal:

```text
Q1
Q2
Q2.1
Q3
Q3.1
Q4
```

Não reorganizar por tecnologia, domínio, complexidade, relevância ou resultado futuro.

## 18. Rastreabilidade

Toda pergunta extraída deve poder ser relacionada ao trecho original:

```yaml
source:
  transcript_segment_ids:
    - S014
    - S015
  original_text: "Você já trabalhou com... ...Application Insights?"
```

Quando possível, manter também a origem temporal conforme o Stage 20:

```yaml
source:
  start: "08:41"
  end: "08:57"
```

Não criar pergunta sem origem rastreável. Quando a origem estiver ausente, registrar a limitação e marcar `needs_review: true`.

## 19. Modelo de dados

O modelo reutiliza `question_id`, `source`, `follow_up_of`, `question_status` e `needs_review` previstos no Stage 20. Os campos específicos desta etapa são somente os necessários para distinguir o texto original da forma estruturada e a confiança da extração.

```yaml
question:
  question_id: Q07
  speaker:
    participant_id: P02
    attribution_confidence: high
  text: "Você já trabalhou com Application Insights?"
  original_text: "Você já trabalhou com application inside?"
  question_status: identified
  response_status: missing
  extraction_confidence: medium
  follow_up_of: null
  reformulation_of: null
  source:
    transcript_segment_ids:
      - S014
    start: "08:41"
    end: "08:57"
  needs_review: true
  review_reason: "Termo técnico normalizado; texto original preservado."
```

`response_status` pode ser preenchido como `missing` quando o trecho termina sem resposta identificável, sem implicar ausência de conhecimento. O `response` em si pertence ao `Response Extraction` e ao vínculo posterior; não deve ser inventado neste módulo.

Não adicionar campos de score, taxonomia, avaliação, evidência ou senioridade.

## 20. Casos de teste obrigatórios

### Caso 1 — Pergunta explícita

```text
Entrevistador:
Você já trabalhou com Java 17?
```

Resultado:

```yaml
question_id: Q1
speaker:
  participant_id: interviewer
question: "Você já trabalhou com Java 17?"
question_status: identified
extraction_confidence: high
```

### Caso 2 — Pergunta sem interrogação

```text
Entrevistador:
Me explica como você utilizaria o Azure Monitor.
```

Resultado: extrair uma pergunta, mesmo sem `?`, porque a fala solicita uma explicação.

### Caso 3 — Pergunta de cenário

```text
Entrevistador:
A aplicação começou a apresentar aumento de latência.
Como você investigaria esse problema?
```

Resultado: uma pergunta de cenário, com os dois segmentos preservados na origem. Não classificar aqui como `troubleshooting`; isso pertence à [[Question Taxonomy]].

### Caso 4 — Follow-up

```text
Entrevistador:
Você já trabalhou com Java?

Candidato:
Sim.

Entrevistador:
Qual versão?
```

Resultado:

```yaml
question_id: Q1
question_status: identified

question_id: Q1.1
follow_up_of: Q1
question_status: identified
```

### Caso 5 — Pergunta composta

```text
Entrevistador:
Você já trabalhou com Azure?
Quais serviços utilizou e em quais situações?
```

Decisão esperada: manter como uma unidade composta se a fala for contínua e a segunda frase detalhar a primeira. Separar em `Q1` e `Q1.1` somente se houver evidência de solicitações independentes ou respostas separadas. Registrar `needs_review` se a separação não for clara.

### Caso 6 — Reformulação

```text
Entrevistador:
Você já trabalhou com Kubernetes?

Entrevistador:
Quer dizer, já trabalhou com algum orquestrador de containers?
```

Resultado:

```yaml
question_id: Q1
question_status: identified

question_id: Q1.1
reformulation_of: Q1
question_status: identified
```

Preservar as duas formulações.

### Caso 7 — Pergunta interrompida

```text
Entrevistador:
Você já trabalhou com...

Candidato:
Sim.

Entrevistador:
...Application Insights?
```

Resultado: unir os segmentos somente se a autoria e a continuidade sustentarem a mesma pergunta. Marcar `partially_identified` ou `needs_review` se a ligação depender de reconstrução posterior. Não completar o conteúdo ausente.

### Caso 8 — Pergunta parcialmente transcrita

```text
Entrevistador:
Como você faria para investigar...
```

Resultado:

```yaml
question_status: partially_identified
extraction_confidence: medium
needs_review: true
```

Preservar somente o texto existente.

### Caso 9 — Erro de transcrição

```text
Entrevistador:
Você já trabalhou com Azure Montor?
```

Normalizar para `Azure Monitor` somente se o contexto tornar o termo inequívoco. Caso contrário, manter o original, registrar a ambiguidade e usar `needs_review: true`.

### Caso 10 — Pergunta do candidato

```text
Candidato:
Como funciona o processo de deploy?
```

Resultado:

```yaml
speaker:
  participant_id: candidate
question_status: identified
```

A pergunta é extraída, mas não é automaticamente uma pergunta técnica de avaliação.

### Caso 11 — Pergunta sem resposta

```text
Entrevistador:
Você já utilizou Application Insights?
```

Sem resposta posterior:

```yaml
question_status: identified
response_status: missing
```

Não inferir falta de conhecimento ou motivo para a ausência.

### Caso 12 — Afirmação e pergunta

```text
Entrevistador:
Aqui usamos bastante Azure Monitor.
Você já trabalhou com ele?
```

Resultado: preservar a primeira frase como contexto/afirmação e extrair somente a segunda como pergunta.

### Caso 13 — Pergunta e comentário

```text
Entrevistador:
Você já trabalhou com Java 21?
É algo que usamos bastante aqui.
```

Resultado: somente a primeira frase é a pergunta; o comentário permanece separado.

### Caso 14 — Pergunta retórica

```text
Entrevistador:
A gente não deveria olhar os logs primeiro?
```

Resultado: preservar como pergunta, sem classificá-la automaticamente como avaliativa e sem presumir que o candidato deveria responder.

### Caso 15 — Trecho ambíguo

```text
Entrevistador:
Você chegou a...

[trecho ilegível]
```

Resultado:

```yaml
question_status: uncertain
extraction_confidence: low
needs_review: true
```

Não completar a formulação com base na tecnologia mais provável.

## 21. Gate de validação

O módulo contribui para o gate geral do Stage 20:

```text
READY
READY_WITH_WARNINGS
BLOCKED
```

### READY

- perguntas principais identificadas;
- origem e speaker disponíveis para a maioria das perguntas;
- sequência suficientemente clara;
- sem ambiguidades estruturais críticas.

### READY_WITH_WARNINGS

- perguntas parcialmente transcritas ou ambíguas;
- alguns segmentos `unknown`;
- dúvidas pontuais sobre perguntas compostas, reformulações ou follow-ups;
- estrutura ainda utilizável sem fabricar conteúdo.

### BLOCKED

- a estrutura das perguntas não pode ser reconstruída com segurança;
- a sequência está severamente corrompida;
- não é possível distinguir perguntas de afirmações na maior parte da entrevista;
- grande parte do material está ilegível ou sem origem.

`BLOCKED` descreve um problema estrutural de processamento. Não significa candidato reprovado, ausência de conhecimento ou entrevista tecnicamente ruim.

## 22. Critérios de qualidade

O módulo deve garantir que:

- toda pergunta extraída tenha origem rastreável;
- o speaker da pergunta seja preservado;
- perguntas do candidato sejam diferenciadas das perguntas dos entrevistadores;
- follow-ups e reformulações mantenham suas relações;
- perguntas compostas não sejam divididas artificialmente;
- perguntas interrompidas permaneçam incompletas quando necessário;
- erros claros possam ser normalizados sem apagar o original;
- ambiguidades sejam preservadas;
- `unknown` e `needs_review` sejam permitidos;
- a ordem temporal seja mantida;
- os `question_id` sejam estáveis;
- a base técnica não seja usada como gabarito ou fonte de conteúdo ausente;
- nenhuma avaliação técnica ocorra nesta etapa;
- pergunta sem resposta não seja interpretada como ausência de conhecimento.

## 23. Regra de ouro

> **É preferível preservar uma pergunta como parcial ou ambígua do que inventar uma formulação que não está presente na transcrição.**

> **A pergunta extraída deve representar o que foi efetivamente perguntado, não o que o avaliador acredita que deveria ter sido perguntado.**

## 24. Integração com o pipeline

```text
20.1 — Participant Identification
→ identifica os participantes

20.2 — Speaker Attribution
→ identifica quem falou cada trecho

20.3 — Question Extraction
→ identifica quais trechos constituem perguntas

20.4 — Response Extraction
→ identifica quais trechos constituem respostas

20.5 — Reconstruction & Normalization
→ trata reconstrução e normalização de conteúdo

20.6 — Question/Response Linking
→ relaciona perguntas e respostas

20.7 — Validation
→ verifica consistência estrutural

Structured Interview
→ entrada para Evidence Model / Evaluation Engine
```

O `20.3` fornece perguntas estruturadas, speakers, IDs, relações e origem para as etapas seguintes. Não assume responsabilidade por extrair respostas, reconstruir conteúdo ausente, classificar perguntas, criar evidências ou avaliar o candidato.
