# 20.6 — Question-Response Linking

Esta etapa define como relacionar perguntas e respostas já extraídas e reconstruídas nos módulos anteriores.

Ela recebe as estruturas de [[20.3 - Question Extraction]], [[20.4 - Response Extraction]] e [[20.5 - Reconstruction & Normalization]], preservando os participantes e a autoria definidos em [[20.1 - Participant Identification]] e [[20.2 - Speaker Attribution]].

## 1. Objetivo e fluxo

A pergunta central desta etapa é:

```text
Qual resposta pertence a qual pergunta ou follow-up?
```

```text
20.1 Participant Identification
↓
Quem são os participantes?

20.2 Speaker Attribution
↓
Quem disse cada segmento?

20.3 Question Extraction
↓
Quais são as perguntas?

20.4 Response Extraction
↓
Quais são as respostas?

20.5 Reconstruction & Normalization
↓
Como representar as falas de forma legível?

20.6 Question/Response Linking
↓
Como perguntas e respostas se relacionam?

20.7 Validation
↓
A estrutura completa é consistente?

Evidence Model
↓
Quais evidências existem?

Evaluation Engine
↓
Como avaliar essas evidências?
```

O linking conecta unidades já identificadas. Ele não cria conteúdo, não altera o texto, não corrige atribuição de speaker e não avalia a resposta.

## 2. Separação de responsabilidades

> **Linking não é avaliação.**

O Stage 20.6 não deve decidir se uma resposta é boa, ruim, correta, incorreta, completa, profunda ou tecnicamente relevante. Sua responsabilidade termina na relação estrutural entre perguntas, follow-ups e respostas.

Também não deve:

- criar uma pergunta para acomodar uma resposta;
- vincular respostas usando apenas conhecimento técnico;
- alterar `speaker attribution`;
- alterar `reconstruction`;
- consultar a avaliação posterior para decidir o vínculo;
- transformar proximidade temática em prova de relação;
- interpretar a ausência de vínculo como ausência de conhecimento.

## 3. Princípio fundamental

Uma relação `question → response` somente deve ser criada quando houver evidência suficiente na estrutura da entrevista.

Não forçar o vínculo apenas porque:

- a resposta veio depois da pergunta;
- o candidato falou sobre tema semelhante;
- a resposta parece tecnicamente adequada;
- a fala seria uma boa resposta para aquela pergunta;
- a pergunta anterior está sem resposta e existe uma fala próxima.

A proximidade temporal é importante, mas não é suficiente em todos os casos.

> **O linking deve representar a relação que a entrevista sustenta, não a relação que parece tecnicamente conveniente.**

## 4. Hierarquia de evidências

Usar a seguinte prioridade, da evidência mais forte para a mais fraca:

1. Relação explicitamente indicada na estrutura da transcrição;
2. `follow_up_of` explicitamente relacionado;
3. Continuidade conversacional inequívoca;
4. Resposta imediatamente posterior sem outra pergunta concorrente;
5. Estrutura clara `pergunta → resposta`;
6. Referências explícitas, como `"nesse caso"` ou `"como falei antes"`;
7. Contexto temático imediato;
8. Inferência estrutural limitada.

Quanto mais baixa a evidência, maior a necessidade de:

```yaml
linking_confidence:
  level: low
needs_review: true
```

Conhecimento técnico pode ajudar a entender uma frase, mas não deve ser a evidência principal para inventar o vínculo.

## 5. Relação básica

```text
Q1:
O que é injeção de dependência?

R1:
É uma forma de fornecer dependências externamente.
```

Resultado:

```yaml
link:
  question_id: Q1
  response_id: R1
  relation_type: answer
  linking_confidence:
    level: high
  needs_review: false
```

## 6. Resposta composta

Quando o Stage 20.4 já determinou que vários segmentos pertencem a uma única resposta, o linking deve preservar essa decisão:

```text
Q1 → R1

R1.source.segment_ids:
  - S12
  - S13
  - S14
```

Não converter artificialmente em:

```text
Q1 → R1
Q1 → R2
Q1 → R3
```

Os segmentos continuam compondo a mesma resposta.

## 7. Uma pergunta com múltiplas intervenções

```text
Q1: Como você resolveria isso?
Candidate: Eu verificaria os logs.
Interviewer: E depois?
Candidate: Verificaria as métricas.
```

Se `"E depois?"` for continuação da mesma investigação, o linking deve preservar:

```text
Q1
├── R1
└── Q1.1
    └── R2
```

Se 20.3 não criou uma nova pergunta para `"E depois?"`, não criar uma durante o linking. Nesse caso, manter múltiplos segmentos ou respostas relacionadas a `Q1`, conforme a estrutura existente, e marcar revisão se a relação não estiver clara.

## 8. Follow-ups

Follow-ups preservam a hierarquia:

```text
Q5:
Como você faria o troubleshooting?

R5:
Eu começaria pelos logs.

Q5.1:
E se não encontrasse nada nos logs?

R6:
Eu verificaria métricas e traces.
```

```yaml
links:
  - question_id: Q5
    response_id: R5
    relation_type: answer
  - question_id: Q5.1
    response_id: R6
    relation_type: follow_up_answer
    follow_up_of: Q5
```

O linking não deve transformar `Q5.1` em pergunta independente nem remover `follow_up_of`.

## 9. Reformulações

Uma reformulação não é automaticamente uma nova pergunta independente:

```text
Q1: Como você faria o deploy?
R1: Eu usaria CI/CD.
Q1.1: Digo, como faria o deploy dessa aplicação especificamente?
R2: Eu configuraria o pipeline do projeto.
```

Quando 20.3 tiver registrado:

```yaml
reformulation_of: Q1
```

preservar essa relação. O vínculo de `R2` deve apontar para a pergunta reformulada quando a resposta vier depois dela:

```yaml
question_id: Q1.1
response_id: R2
relation_type: reformulation
```

`reformulation` descreve a relação estrutural da pergunta; não significa que a resposta seja correta ou que a primeira pergunta tenha sido inválida.

## 10. Pergunta sem resposta

```text
Q3:
Como funciona Application Insights?

[nenhuma resposta identificável]

Q4:
Vamos para outra.
```

Resultado:

```yaml
question_id: Q3
response_id: null
response_status: missing
```

Isso significa apenas que não foi localizada uma resposta. Não significa que o candidato não sabe, recusou-se a responder ou falhou.

## 11. Resposta sem pergunta

```text
Candidate:
Eu verificaria primeiro as dependências.
```

Se não for possível identificar a pergunta:

```yaml
response_id: R7
question_id: unknown
question_status: missing
needs_review: true
```

Não inventar uma pergunta provável. A resposta permanece preservada e rastreável.

## 12. Uma resposta potencialmente relacionada a várias perguntas

```text
Q1: Como você monitoraria a aplicação?
Q2: Como investigaria uma latência alta?

Candidate:
Eu começaria olhando logs, métricas e traces.
```

Não vincular automaticamente `R1` a `Q1` e `Q2`. Se não houver evidência para distinguir:

```yaml
question_id: unknown
needs_review: true
review_reason: "O segmento pode responder a Q1 ou Q2; a transcrição não permite decidir."
```

Se a estrutura suportar hipóteses múltiplas, elas devem ser registradas como hipóteses de linking, nunca como vínculos confirmados. Caso contrário, usar `unknown`.

## 13. Resposta que continua após follow-up

```text
Q1: Como você faria isso?
Candidate: Eu usaria uma fila porque—
Interviewer: Por que uma fila?
Candidate: Porque o processamento pode ser assíncrono.
```

Preservar o vínculo estrutural:

```text
Q1  → resposta inicial
Q1.1 → resposta ao follow-up
```

O segundo trecho pode ser uma resposta a `Q1.1` e também uma continuação semântica da resposta inicial. Não apagar a relação entre as partes e não criar uma resposta independente se 20.4 já as agrupou.

Quando a transcrição não permitir distinguir complemento de nova resposta:

```yaml
linking_confidence:
  level: low
needs_review: true
```

## 14. Follow-up que muda o assunto

```text
Q1: Como você resolveria o timeout?
R1: Eu verificaria as dependências.

Q2: Você já trabalhou com Kubernetes?
```

`Q2` é uma nova pergunta quando não existe relação de aprofundamento com `Q1`. O linking deve respeitar a mudança de assunto e não usar apenas a proximidade temporal para classificá-la como follow-up.

## 15. Pergunta do candidato

```text
Interviewer:
Como você implementaria isso?

Candidate:
Eu usaria uma fila. Posso perguntar uma coisa sobre o ambiente?
```

O primeiro trecho pode ser resposta de `Q1`. O segundo é pergunta do candidato e deve permanecer sob responsabilidade do [[20.3 - Question Extraction]].

Não vincular a pergunta do candidato a `Q1` como se fosse resposta. Se houver um texto misto na mesma unidade de resposta, manter a separação já produzida pelo Stage 20.4.

## 16. Resposta do entrevistador

```text
Interviewer:
Você usaria Application Insights?

Candidate:
Sim.

Interviewer:
Também temos Log Analytics integrado.
```

O último trecho pertence ao entrevistador, conforme 20.2. Não vinculá-lo como resposta do candidato. Pode ser comentário contextual, complemento ou informação da entrevista, mas essa classificação não deve ser inventada no linking.

## 17. Relação temporal

A sequência temporal é relevante:

```text
Q1
↓
R1
↓
Q1.1
↓
R2
```

Podem existir intervenções entre pergunta e resposta:

```text
Q1
↓
intervenção do entrevistador
↓
R1
```

Não assumir que a fala imediatamente posterior sempre responde à pergunta imediatamente anterior. Verificar novas perguntas, comentários, interrupções, mudanças de assunto e autoria.

## 18. Confidence do linking

Usar um campo específico:

```yaml
linking_confidence:
  level: high | medium | low
```

- `high`: relação explícita, inequívoca e sem pergunta concorrente;
- `medium`: relação plausível, mas existe interrupção, intervenção ou pequena ambiguidade;
- `low`: existem relações concorrentes ou a estrutura não permite decisão segura.

`linking_confidence` mede apenas a segurança da relação pergunta ↔ resposta:

```text
extraction_confidence
→ segurança na extração da resposta

reconstruction_confidence
→ segurança na forma reconstruída

linking_confidence
→ segurança na relação pergunta ↔ resposta

evaluation_confidence
→ segurança da avaliação técnica posterior
```

Esses campos não são intercambiáveis.

## 19. Ambiguidade e conflito

Quando houver duas relações plausíveis:

```text
Q1 → R1
Q2 → R1
```

o agente deve:

1. identificar o conflito;
2. registrar as evidências disponíveis;
3. comparar a força das evidências;
4. escolher somente quando houver suporte suficiente;
5. reduzir `linking_confidence` quando a relação for apenas provável;
6. usar `question_id: unknown` se não houver base suficiente;
7. marcar `needs_review: true` quando a incerteza for relevante.

Não ocultar o conflito nem selecionar a relação mais conveniente tecnicamente.

## 20. Estrutura hierárquica

O modelo deve suportar mais do que uma lista linear:

```text
Q1
└── R1

Q2
├── R2
└── Q2.1
    └── R3

Q3
├── R4
├── Q3.1
│   └── R5
└── Q3.2
    └── R6
```

Perguntas compostas, subperguntas, follow-ups e reformulações devem ser preservados conforme foram identificados no Stage 20.3. O 20.6 relaciona estruturas existentes; não redefine a pergunta nem cria subperguntas novas.

## 21. Tipos de relação

Usar os seguintes tipos estruturais, somente quando sustentados:

```text
answer
follow_up_answer
reformulation
clarification
continuation
unknown
```

- `answer`: resposta direta à pergunta;
- `follow_up_answer`: resposta ao follow-up identificado;
- `reformulation`: relação com pergunta reformulada, quando 20.3 tiver registrado essa relação;
- `clarification`: resposta a uma pergunta de esclarecimento;
- `continuation`: continuação de uma resposta ou relação já estabelecida;
- `unknown`: relação não determinável.

Esses tipos não expressam qualidade, correção, completude ou relevância técnica.

## 22. Modelo de dados

O modelo reutiliza `question_id`, `response_id`, `follow_up_of`, `question_status`, `response_status`, `source` e `needs_review` já definidos nos módulos anteriores.

```yaml
link:
  question_id: Q1
  response_id: R1
  relation_type: answer
  linking_confidence:
    level: high
  needs_review: false
  review_reason: null
  source:
    question_segment_ids:
      - S10
    response_segment_ids:
      - S11
      - S12
```

Para follow-up:

```yaml
link:
  question_id: Q1.1
  response_id: R2
  relation_type: follow_up_answer
  follow_up_of: Q1
  linking_confidence:
    level: high
  needs_review: false
```

Para pergunta sem resposta:

```yaml
link:
  question_id: Q3
  response_id: null
  relation_type: unknown
  response_status: missing
  linking_confidence:
    level: high
  needs_review: false
```

Para resposta sem pergunta:

```yaml
link:
  question_id: unknown
  response_id: R7
  relation_type: unknown
  question_status: missing
  needs_review: true
```

`source` deve manter a origem da pergunta e da resposta. O linking não substitui nem altera `source` das unidades originais.

## 23. Validação

Antes de encaminhar a estrutura para o Stage 20.7, verificar:

1. Toda pergunta pode ter zero ou mais respostas conforme a estrutura da entrevista.
2. Toda resposta possui `response_id`.
3. Uma resposta não foi vinculada arbitrariamente a várias perguntas.
4. Follow-ups mantêm `follow_up_of`.
5. Reformulações preservam a relação correta.
6. Perguntas sem resposta possuem `response_status: missing`.
7. Respostas sem pergunta possuem `question_id: unknown` quando aplicável.
8. `speaker attribution` não foi alterado pelo linking.
9. A reconstrução e o texto não foram alterados pelo linking.
10. `linking_confidence` permanece separado dos demais confidence.
11. Ambiguidades possuem `needs_review` e justificativa quando necessário.
12. Não existem relações baseadas apenas em conhecimento técnico.
13. A origem dos segmentos permanece rastreável.
14. O linking não contém avaliação técnica.
15. A estrutura permanece compatível com o [[Evaluation Engine]] sem executar avaliação.

## 24. Testes controlados

Os testes verificam apenas relações estruturais.

### Caso 1 — Pergunta e resposta direta

```text
Q1: O que é injeção de dependência?
R1: É uma forma de fornecer dependências externamente.
```

Resultado:

```yaml
question_id: Q1
response_id: R1
relation_type: answer
linking_confidence:
  level: high
needs_review: false
```

### Caso 2 — Resposta em múltiplos segmentos

```text
Q1: Como você estruturaria o acesso ao repositório?
R1: Eu usaria uma interface.
R1: A implementação ficaria na infraestrutura.
R1: A aplicação dependeria da abstração.
```

Resultado: um único vínculo `Q1 → R1`; os segmentos permanecem dentro de `R1.source.segment_ids`.

```yaml
relation_type: answer
linking_confidence:
  level: high
needs_review: false
```

### Caso 3 — Resposta interrompida

```text
Q1: Onde você colocaria o processamento?
R1: Eu faria dentro do serviço e—
Interviewer: Dentro do domínio ou da aplicação?
```

Resultado:

```yaml
question_id: Q1
response_id: R1
relation_type: answer
linking_confidence:
  level: medium
needs_review: true
```

A interrupção deve permanecer na origem de `R1`.

### Caso 4 — Follow-up e resposta

```text
Q5: Como você faria o troubleshooting?
R5: Eu começaria pelos logs.
Q5.1: E se não encontrasse nada?
R6: Eu verificaria métricas e traces.
```

Resultado:

```yaml
- question_id: Q5
  response_id: R5
  relation_type: answer
- question_id: Q5.1
  response_id: R6
  relation_type: follow_up_answer
  follow_up_of: Q5
```

Ambos com `linking_confidence: high` quando a sequência for inequívoca.

### Caso 5 — Reformulação

```text
Q1: Como você faria o deploy?
R1: Eu usaria CI/CD.
Q1.1: Digo, como faria o deploy dessa aplicação especificamente?
R2: Eu configuraria o pipeline do projeto.
```

Resultado: `R2` vinculado a `Q1.1`, preservando `reformulation_of: Q1` e usando `relation_type: reformulation` quando essa relação tiver sido identificada em 20.3.

### Caso 6 — Pergunta sem resposta

```text
Q3: Como funciona Application Insights?
Q4: Vamos para outra.
```

Resultado:

```yaml
question_id: Q3
response_id: null
response_status: missing
needs_review: false
```

Não criar resposta nem inferir desconhecimento.

### Caso 7 — Resposta sem pergunta

```text
R7: Eu verificaria primeiro as dependências.
```

Resultado:

```yaml
question_id: unknown
response_id: R7
relation_type: unknown
question_status: missing
needs_review: true
```

Não criar uma pergunta provável.

### Caso 8 — Duas perguntas próximas e resposta ambígua

```text
Q1: Como você monitoraria a aplicação?
Q2: Como investigaria uma latência alta?
R8: Eu começaria olhando logs, métricas e traces.
```

Resultado: não vincular automaticamente a Q1 ou Q2.

```yaml
question_id: unknown
response_id: R8
relation_type: unknown
linking_confidence:
  level: low
needs_review: true
```

### Caso 9 — Resposta que continua após follow-up

```text
Q1: Como você faria isso?
R1: Eu usaria uma fila porque—
Q1.1: Por que uma fila?
R2: Porque o processamento pode ser assíncrono.
```

Resultado:

```yaml
- question_id: Q1
  response_id: R1
  relation_type: answer
- question_id: Q1.1
  response_id: R2
  relation_type: follow_up_answer
  follow_up_of: Q1
```

Preservar a continuidade sem transformar R2 em resposta sem relação com R1.

### Caso 10 — Mudança clara de assunto

```text
Q1: Como resolveria o timeout?
R1: Eu verificaria as dependências.
Q2: Você já trabalhou com Kubernetes?
R2: Sim, em outro projeto.
```

Resultado: `Q2 → R2` não é follow-up de Q1; é relação independente.

### Caso 11 — Pergunta do candidato

```text
Q1: Como você implementaria isso?
R1: Eu usaria uma fila. Posso perguntar uma coisa sobre o ambiente?
Q2: Como funciona o deploy?
```

Resultado: vincular somente a parte resposta de R1 a Q1. A pergunta do candidato deve ser preservada como Q2 ou como unidade separada já produzida por 20.3.

### Caso 12 — Comentário do entrevistador

```text
Q1: Você usaria Application Insights?
R1: Sim.
Interviewer: Também temos Log Analytics integrado.
```

Resultado: `Q1 → R1`. O comentário do entrevistador não é resposta adicional do candidato.

### Caso 13 — Pergunta composta

```text
Q1: O que é Kubernetes e quais são suas vantagens?
R1: Kubernetes é uma plataforma para gerenciar containers.
```

Resultado: um vínculo `Q1 → R1`; não criar subperguntas durante o linking. `R1.response_status` permanece `partial` conforme 20.4.

### Caso 14 — Resposta parcial a pergunta composta

```text
Q1: O que é X e quais são suas vantagens?
R1: X é uma forma de organizar o código.
```

Resultado:

```yaml
question_id: Q1
response_id: R1
relation_type: answer
response_status: partial
linking_confidence:
  level: high
needs_review: false
```

O linking não cria uma nova pergunta para a parte ausente.

### Caso 15 — Relação ambígua

```text
Q1: Como você investigaria os erros?
Q2: Como você acompanharia a saúde da aplicação?
R1: Eu olharia os dashboards primeiro.
```

Resultado:

```yaml
question_id: unknown
response_id: R1
relation_type: unknown
linking_confidence:
  level: low
needs_review: true
review_reason: "O trecho pode responder a Q1 ou Q2; a transcrição não sustenta uma escolha."
```

## 25. Gates

O Stage 20.6 participa do gate geral:

```text
READY
READY_WITH_WARNINGS
BLOCKED
```

### READY

- perguntas e respostas estão majoritariamente conectadas;
- os vínculos são sustentados pela transcrição;
- follow-ups e reformulações estão preservados;
- a rastreabilidade está intacta;
- não há ambiguidade estrutural relevante.

### READY_WITH_WARNINGS

- existem relações ambíguas pontuais;
- existem respostas sem pergunta;
- existem perguntas sem resposta;
- alguns follow-ups possuem relação incerta;
- a estrutura geral permanece utilizável sem inventar contexto.

### BLOCKED

- não é possível estabelecer as relações principais;
- a ordem da entrevista está severamente comprometida;
- perguntas e respostas estão estruturalmente misturadas;
- estabelecer os vínculos exigiria inventar contexto;
- a maioria das relações dependeria de conhecimento técnico externo.

`BLOCKED` significa insuficiência estrutural do processamento. Não significa candidato reprovado, ausência de conhecimento ou resposta tecnicamente ruim.

## 26. Critérios de qualidade

O Stage 20.6 é saudável quando:

- cada relação pergunta ↔ resposta é justificável;
- perguntas sem resposta são preservadas;
- respostas sem pergunta são preservadas;
- follow-ups são hierarquizados;
- reformulações são diferenciadas;
- respostas compostas continuam agrupadas;
- ambiguidades permanecem explícitas;
- `speaker attribution` não é alterado;
- `reconstruction` não é alterada;
- não há avaliação técnica;
- não há conteúdo inventado;
- toda relação possui rastreabilidade;
- `linking_confidence` é independente das demais confianças;
- o modelo está pronto para a validação final do Stage 20.7.

## 27. Regra de ouro

> **O linking deve representar a relação que a entrevista sustenta, não a relação que parece tecnicamente conveniente.**

> **Quando não houver evidência suficiente para estabelecer uma relação pergunta → resposta, preserve a incerteza em vez de criar um vínculo artificial.**

## 28. Integração com o pipeline

```text
20.1 — Participant Identification
→ identifica participantes

20.2 — Speaker Attribution
→ identifica autoria dos segmentos

20.3 — Question Extraction
→ identifica perguntas

20.4 — Response Extraction
→ identifica respostas

20.5 — Reconstruction & Normalization
→ preserva forma legível sem alterar significado

20.6 — Question/Response Linking
→ relaciona perguntas, follow-ups e respostas

20.7 — Validation
→ verifica consistência estrutural completa

Structured Interview
→ entrada para Evidence Model / Evaluation Engine
```

O Stage 20.6 fornece vínculos, hierarquia, tipo de relação, confiança e rastreabilidade. Não redefine perguntas, não reconstrói respostas e não avalia evidências.
